## Current release blockers

1. `index.js:667` deliberately returns HTTP 404 for `quickBooksCommerceWebhook`; it never invokes the standalone processor. Parent reports the live endpoint also returns 404. I did not probe or configure production.
2. `providers/quickbooks-webhooks.js:20` correctly verifies exact raw-byte HMAC-SHA256 with timing-safe comparison. However, `:90` requires a legacy `eventNotifications` object and rejects signed CloudEvents arrays. Intuit now documents arrays with `id`, `type`, `time`, `intuitentityid` and `intuitaccountid`, with potentially different companies per event. [Current Intuit configuration guide](https://static.developer.intuit.com/output_html/qbo/docs/develop/webhooks/configure-webhooks.html). Intuit's official migration article gives the extended deadline as July 31, 2026, which has passed. [Intuit migration notice](https://medium.com/intuitdev/upcoming-change-to-webhooks-payload-structure-2a87dab642d0).
3. The processor hashes normalized entity hints rather than retaining CloudEvent IDs. Batch hint persistence (`order-repository.js:551`) sets documents, and consumption deletes them. Replays can recreate a consumed hint. Payment/order transactions prevent duplicate initial fulfillment, but a durable event receipt is still needed for current payload replay handling.
4. Fulfilled orders are reconciliation-terminal (`order-state.js:61`, `commerce-service.js:735`). Later payment void/delete or refund changes do not automatically revalidate an active entitlement. CDC currently covers only Invoice and Payment (`providers/quickbooks.js:672`), and the standalone parser also allowlists only those entities. Refund/credit/chargeback and account-access policy requires additional supported evidence and an explicit revocation path.
5. Catalog capability values (`catalog.js:11`) are static assertions from prior work; `active:false` and `release.deployApproved:false` remain set. All four feature flags default false (`feature-flags.js`). Parent's current read confirms The Ballers Kingdom company and an empty payment-methods result. That result neither proves nor disproves merchant support. Obtain fresh runtime Accounting health and supported merchant/payment-delivery evidence before activation; do not advertise card/ACH/wallet availability from these hardcoded booleans.
6. No course enrollment, lesson catalog, private course viewer, learning progress or subscription lifecycle exists in the audited commerce source. Base44 links are an interim discovery route, not the requested Firebase app system.

## Smallest safe Firebase phase

Keep Firebase Hosting, the existing Firebase Auth identity, Firestore, Storage and Functions. Add a native assessment with versioned deterministic scoring and transparent recommendation rules. Allow a guest to complete it in memory; save to the existing user's private space only after explicit save/consent. Send no assessment answers or workout journals to QuickBooks. An AI recommendation provider can be added later through a bounded server adapter after its provider, cost and sharing choices are approved.

The intended journey is native assessment, recommendation, server catalog, sign-in, order reservation, order-specific QuickBooks invoice, verified payment evidence, atomic entitlement, private course/guide access, then progress and delivery ledger. Preserve the current invoice/email flow for the first approved guide, with purchasing inactive until the current merchant path is proven. A native preview may show synthetic order states and locked course placeholders; it must disclose simulation.

Proposed additions are versioned public product/lesson metadata, private `assessmentRuns`, server-owned course `enrollments` associated with order/SKU/content version, and bounded owner `learningProgress`. Return a minimal owner view through authenticated Functions; financial and provider references remain server-only. Check active enrollment and order eligibility on each content request. Never store cards, tokens or OAuth secrets in the browser. Keep the personal Ballers QuickBooks realm and server identity isolated from other companies.

Before paid activation, implement a bounded CloudEvents adapter that verifies raw bytes before parsing, validates event type/version/time/IDs, checks each event's authorized realm, and records durable receipts keyed by realm plus event ID. Persist authorized hints before acknowledging; process provider reads in the worker. Unsupported or foreign events must not create orders or access. Test mixed realms, duplicates across batches, out-of-order events, malformed events, durable-write failure and retries. Never trust event order or payload as payment authority. Add a saved CDC checkpoint/backfill strategy and operator alerts; the current rolling 24-hour window alone is insufficient evidence after a longer outage.

Define full refund, partial refund, void/delete, dispute and cancellation policies before activation. Confirmed full revocation should atomically update order/enrollment, invalidate unused grants and append an audit event. Existing downloaded copies cannot be recalled. Partial/ambiguous evidence needs an explicit hold/manual-review policy. Brian selected one-time course/guide purchases first; recurring membership is a later phase requiring renewal, failed payment, cancellation, expiry and proration behavior. No new price, tax, payment account, subscription, OAuth grant, transaction or commerce deployment is authorized by this audit.
